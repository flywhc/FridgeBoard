# FridgeBoard 分会话开发执行计划

状态：P3–P10 已实施；P7.1 已实施，待人工验收；P12 已完成；P13.1–P13.5 已实施，P13.3–P13.5 待真实设备验收，P13.6 进行中
更新日期：2026-08-15
适用范围：从架构设计到上线前验收；不在本文预先锁定技术栈或部署平台。

## 1. 使用方式

本计划将开发拆为可在独立 Codex 会话中完成的任务包。每个会话只领取一个任务包；完成后更新 [进度看板](../progress-tracker.md)，并在下一会话附上交接摘要。

每个任务包启动时都应提供四项信息：

1. **目标**：要交付的可观察结果。
2. **上下文**：相关文档、UI 草稿、已有代码和前置任务结果。
3. **约束**：不得改变的产品规则、兼容性和安全边界。
4. **完成条件**：要通过的测试、检查和人工验收点。

不要把“写代码”“测试”“评审”和“部署”混为同一个未定义的大任务。复杂或不确定的工作先使用 Plan 模式形成实施计划；行为改变必须有对应自动化测试或明确的手工验收记录。

### 1.1 设计基线

- 功能、交互和可行性基线：[功能设计与可行性分析](../functional-design-and-feasibility.md)。
- 最终 UI 草稿 ID 索引：[功能设计与可行性分析 §17.1](../functional-design-and-feasibility.md#171-已确认的最终-ui-设计稿索引)；直接预览链接：[最终 UI 设计图注册表](../final-ui-designs.md)。
- 同一场景的 Superdesign 历史或探索版本不是实现依据。

### 1.2 每个会话的固定产出

1. 先说明将读取的文档、假设和任务边界；发现需求冲突即停下确认。
2. 只修改当前任务包授权的文件；保留并避开无关的工作区改动。
3. 以测试驱动或至少先写可复现用例的方式实现行为和核心规则。
4. 运行与改动相称的单元、集成、类型、格式或端到端检查。
5. 交接时记录：改动、验证命令与结果、未验证项、风险/待决策、下一任务的输入。

### 1.3 后续任务的交付顺序与人工验收规则

- **用户可见优先**：从 P3 开始，每个任务包都必须让用户能完成一个可感知的动作，不能只交付 API、数据表或“为后续页面准备”的代码。P2 是已完成的基础例外。
- **先手机、后增强、再冰箱端显示**：先让手机端完成创建冰箱、录入和日常查看闭环；相机/AI 是录入增强，不得阻塞手工录入；冰箱端视图只在同一数据闭环已可用后接入。
- **每步可手验**：每个任务包的完成条件必须包含本地启动后的具体操作、输入和预期界面/状态；自动化测试不能替代该条。涉及冰箱端显示设备（例如 Kindle）、PWA 安装、相机或推送时，手验必须注明实机和浏览器。
- **可演示边界**：下一任务不能依赖“尚未可操作的 UI”。如果仅有内部能力，必须在同一任务中加一个最小界面或明确调整任务拆分。
- **区分验证与 Spike**：已经有可用实现和人工降级路径的能力，使用真实设备/真实样本做验收，并闭环发现的问题；不要事后把它重排为前置 Spike。只有验证结果仍可能改变功能是否立项、技术路线、数据模型或降级边界时，才单独创建方案 Spike，并在该功能实现前完成。

## 2. 里程碑与任务包

| 里程碑 | 目标 | 进入条件 | 退出条件 |
| --- | --- | --- | --- |
| M0 架构冻结 | 决定可实现的技术边界与 ADR | UI 已确认 | ADR、数据边界和质量门禁已评审 |
| M1 可运行骨架 | 项目可本地启动并持续验证 | M0 | CI 基线、测试骨架、配置策略可用 |
| M2 冰箱与库存闭环 | 创建冰箱、录入、查看、编辑和删除库存 | M1 | 手机端核心库存路径通过 |
| M3 冰箱端显示与无账号配对 | 冰箱端视图与手机配对可用 | M2 | 端到端配对、权限撤销和低频同步通过 |
| M4 食谱与提醒 | 食谱、补货、临期和设备提醒可用 | M2、M3 | 动态扣库存和提醒规则通过 |
| M5 发布准备 | 风险 spike、兼容性和验收完成 | M3、M4 | 发布清单通过，已知限制明确 |

### P0：架构与 ADR（已完成）

- **目标**：选定前端/PWA、服务端、数据库、认证凭证、文件短效 URL、通知、部署和观测方案。
- **输入**：功能设计 §1–18、最终 UI 索引、目标显示设备型号/浏览器范围（例如 Kindle）。
- **输出**：[架构概览](../architecture/README.md)、[ADR 索引](../architecture/adr/README.md)、数据所有权与信任边界图、关键技术风险清单。
- **完成条件**：能解释无账号配对的凭证生命周期、二维码短效策略、Agnes 图片传递与删除、离线/日同步语义；没有未经确认的技术假设。
- **依赖**：无。

### P1：工程骨架与质量门禁

- **目标**：建立项目结构、环境配置约定、开发/测试/格式化/类型检查命令及 CI 最小闭环。
- **输入**：P0 ADR。
- **输出**：可启动的最小应用、样例环境变量说明、测试框架、CI 配置、项目级 `AGENTS.md`（仅写已验证命令与约定）。
- **完成条件**：新环境按 README 可启动；核心命令在干净工作区通过；机密不进入仓库。
- **依赖**：P0。

### P2：领域模型、迁移与核心规则

- **目标**：实现冰箱、布局、分区、食物分类、库存批次、BBD、设备凭证和食谱的领域模型。
- **输入**：P0 数据模型 ADR、功能设计 §4–9 与 §10。
- **输出**：迁移、类型/schema、仓储/服务边界及规则单元测试。
- **完成条件**：覆盖 BBD 可选、临期窗口 clamp、严格小类匹配、BBD 最早优先扣减、撤销可逆、按大类记忆位置。
- **依赖**：P1。

### P3：无账号配对与设备授权

- **目标**：实现短效二维码会话、PWA 自动配对、独立设备凭证、撤销和重新加入。
- **输入**：P0 安全 ADR、P2 设备与冰箱模型、UI 草稿“配对/冰箱管理/冰箱切换”。
- **输出**：可在手机端实际操作的所有者登录、冰箱端兼容绑定码/二维码配对页、设备列表与移除操作；配套配对 API、凭证存储/轮换策略、访问控制和端到端测试。
- **完成条件**：非 PWA 不配对；PWA 扫码不需二次确认；移除设备后不能访问；重新扫码可恢复。
- **人工验收**：在两台浏览器实例中，以所有者创建一个兼容绑定码，并在冰箱端显示设备模拟页面完成绑定；用已安装 PWA 扫描二维码后看到冰箱进入列表；移除该设备，刷新被移除端确认访问被拒绝，再扫码确认恢复。
- **依赖**：P1、P2。

### P4：冰箱模板、布局配置与位置选择

- **目标**：实现七种模板、图形化分格配置与必填存放位置。
- **输入**：P2、最终 UI 草稿“创建冰箱/布局预览/布局分格编辑/确认位置与数量”。
- **输出**：手机端“创建冰箱 → 预览 → 编辑布局 → 保存”路径、模板定义、布局 API、位置选择器和持久化测试。
- **完成条件**：单行区域只允许一格、左右两格、左中右三格；其余纵向区域支持 1–6 层；预览与墨水屏布局同构。
- **人工验收**：在手机 PWA 中选择至少两个模板，直接保存一个、编辑另一个；分别尝试单行和纵向区域的所有合法分格，保存后刷新页面，确认预览和位置选择器一致。
- **依赖**：P2、P3。

### P5：库存、分类与图标库

- **目标**：完成库存 CRUD、两级分类、小类图库、用户自定义小类与图标复用。
- **输入**：P2、P4、最终 UI 草稿“添加食材/小类图库/自定义小类/编辑食材”。
- **输出**：手机端库存列表及手工“添加、编辑、删除”路径、库存 API、分类搜索、图标资产接口和相关测试。
- **完成条件**：首页按小类优先、空间不足降级大类；自定义图标确认后可复用；未填 BBD 不参与风险提醒。
- **人工验收**：手工添加有/无 BBD 的两个同小类批次和一个自定义小类；刷新后确认位置与数量保留、无 BBD 不显示风险、编辑和删除立即更新列表；再次添加同大类食品，确认最近位置被预填且可改写。
- **依赖**：P2、P4。

### P6：相机、条码与 AI 增量识别

- **目标**：实现手机相机、条码识别、Agnes 手工触发识别、字段增量回填与冲突确认。
- **输入**：P0 的 Agnes/媒体安全 ADR、P5、最终 UI 草稿“添加食材/AI 识别确认”。
- **输出**：在既有手机录入页可操作的相机/扫码/AI 辅助入口、浏览器能力降级、短效图片 URL 生命周期、识别适配层、冲突 UI 和契约测试。
- **完成条件**：只写入本次识别到的字段；冲突不静默覆盖；二维码/条码与无包装食品均可走各自路径；媒体按 ADR 删除。
- **人工验收**：在支持相机的手机上分别完成一次条码、包装照片和完全手工录入；拒绝相机权限后确认可继续手填；对已手改字段制造冲突，确认必须选择而非被覆盖；检查任务结束后临时图片不存在。
- **依赖**：P1、P3、P5。

### P7：手机端日常首页与冰箱管理

- **目标**：实现手机冰箱首页、冰箱切换、设备管理、配对二维码入口及设置页。
- **输入**：P3–P5、最终 UI 草稿“当前冰箱首页/冰箱管理/我的冰箱/提醒设置/临期规则”。
- **输出**：响应式 PWA 页面、访问权限 UI、手工刷新状态、设置持久化、页面测试。
- **完成条件**：当前冰箱切换不会串数据；移除设备立即失效；手机首页与已确认 UI 结构一致。
- **人工验收**：至少创建两台冰箱并各录入一件食品，在首页切换三次确认不串数据；从首页进入设备管理并移除测试设备；修改临期设置、刷新和重新打开后确认设置仍生效。
- **依赖**：P3、P4、P5。

### P7.1：冰箱资料、已有布局与删除

- **当前阶段**：实现完成，待人工验收。
- **目标**：补齐已有冰箱的重命名、布局维护、缩减分格时的占用位置自动归位、删除和恢复，解决多个默认名称条目无法辨认及误建冰箱无法移除的问题。
- **输入**：P4、P7、功能设计 §4.3–4.5、[需求及 UI 设计增补](../fridge-management-requirements-and-ui.md)；实施前必须将确认后的场景登记到最终 UI 设计图注册表。
- **评审门禁**：确认同名规则和已有布局编辑范围；删除沿用已接受的 30 天软删除/恢复架构，只需确认“打开 + 设置”列表层级、未绑定冰箱端的兼容绑定码状态、自动归位和删除/恢复页面的文案。
- **输出**：所有者冰箱更新/删除/恢复 API，带并发检查的布局自动归位事务，最近删除清理任务，复用 P4 布局编辑器的手机端管理入口和页面，服务与端到端测试，受影响文档与迁移。
- **完成条件**：普通设备凭证不能执行所有者操作；“打开冰箱”图标进入正确冰箱首页；重命名在各页面和下一次冰箱端同步一致；已有布局复用 P4 编辑器；缩减有食材的分格时库存自动归入该区域最后保留分格；自动归位与布局保存原子；删除立即撤销全部设备；恢复不恢复旧凭证；到期清理可重复执行。
- **自动化验证**：先补失败用例，覆盖所有者/设备权限、名称边界与同名、布局并发冲突、自动归位到最后保留分格、事务回滚、删除/恢复/到期清理、删除当前/最后一台冰箱及列表状态。
- **人工验收**：创建三台默认同名冰箱，确认每台同尺寸的“打开冰箱”图标进入正确首页、齿轮进入正确设置；分别重命名和删除一台；在另一台未绑定冰箱端的设置页生成兼容绑定码；用已有布局进入 P4 编辑器并编辑另一台的空分格和占用分格，确认被删层食材自动归入最后保留层；刷新和切换三次确认不串数据；恢复删除项并确认原设备仍无权访问，重新配对后恢复日常操作；在 320、390、430px 宽度核验全部页面。
- **依赖**：P4、P7、P10 的单实例调度边界。

### P8：冰箱端显示设备视图与低频同步

- **目标**：实现竖屏冰箱端显示设备视图、冰箱分区首页、分区详情、配对二维码和离线状态。
- **输入**：P3–P5、最终 UI 草稿“冰箱端显示设备”四项。
- **输出**：墨水屏路由/样式、分区点击、静态翻页、每日同步与手工刷新、离线标记、实机检查清单。
- **完成条件**：无动画/悬停依赖；食品图标不可单点；同层操作符合已确认两行详情；睡眠后唤醒补同步语义正确。
- **人工验收**：先在桌面窄视口完成首页、分区、数量调整、离线和手动刷新检查，再在目标显示设备实机（例如 Kindle）完成同一流程；让设备睡眠后唤醒，确认当天未同步时补同步并记录截图与固件版本。
- **依赖**：P3、P4、P5。

### P9：食谱、动态补货与库存扣减

- **目标**：实现本周/下周、文本导入、逐日编辑、动态缺货、复制清单、完成扣减和撤销。
- **输入**：P2、P5、最终 UI 草稿“食谱/导入/编辑/补货”。
- **输出**：解析器、严格匹配服务、补货计算、扣减/撤销事务、手机与墨水屏图标状态、测试。
- **完成条件**：七天固定显示；只精确匹配小类；库存变动即时重算；扣减可逆且不误扣。
- **人工验收**：在手机端粘贴一周食谱，逐项改正解析结果；添加/拿走库存确认缺货立即变化；完成一道菜确认按最早 BBD 扣减，再点击撤销确认每个原批次数量恢复；复制缺货清单并检查文本。
- **依赖**：P2、P5；墨水屏补货入口作为 P8 的后续小交付，不阻塞手机闭环。

### P10：提醒、同步与设备健康

- **目标**：实现每日一次食品提醒、提醒时间/关闭、冰箱端日同步、断网重试和手机端设备健康提醒。
- **输入**：P2、P7、P8、P9；开始通知实现前，先用真实 iPhone 主屏幕 PWA 与 Android 安装 PWA 验证可用推送能力及权限流程，并明确应用内提醒降级边界。
- **输出**：任务调度、通知适配、同步状态模型、重试策略、模拟时钟测试与观测日志。
- **完成条件**：临期按 `clamp(ceil(总有效期×20%), 1 天, 14 天)`；无 BBD 不提醒；当日未同步仍通知设备异常；冰箱端非睡眠时才每 30 分钟重试。
- **人工验收**：在手机设置中关闭、重新开启并修改提醒时间；使用模拟时钟走过临期、无 BBD、未同步和重试场景，核对应用内状态与通知；在目标显示设备实机断网后恢复网络，确认重试与状态提示。
- **依赖**：P7、P8、P9。

### P10.5：AI 小类图标生成与审核

- **目标**：让用户为自定义小类生成并选择四个风格一致、可在手机和墨水屏辨识的单色图标；未选择的候选不保留。
- **输入**：P5 的自定义小类与内置图库、功能设计 §15.4、真实目标显示设备或等效一位黑白渲染检查。
- **实施顺序**：本任务开始时先完成一个有时限的方案 Spike，比较受约束 SVG 生成与文生图后矢量/黑白化两条路线；确定候选审核、内容安全、资产格式/大小、临时清理与失败回退后，立即实现选定路线。Spike 失败时必须保留 P5 的内置图库，而不是取消该任务。
- **输出**：生成适配器、四候选确认 UI、只持久化用户选中资产的存储与清理策略、手机/墨水屏渲染、契约与端到端测试。
- **完成条件**：生成失败或审核拒绝时可继续从图库选择；候选在 24/32/48px 和一位黑白下可辨识；仅确认的候选可被后续录入复用，未选候选和临时文件均被删除。
- **人工验收**：创建至少三个特殊小类，分别检查四候选的差异、确认/取消/失败路径，以及手机和目标显示设备上的可读性。
- **依赖**：P5、P10。

### P11：端到端验收与发布准备

- **目标**：在已冻结方案上完成关键链路的端到端验收和发布准备。
- **输入**：P3、P6、P8–P10、P10.5 与功能设计 §15 的真实环境验证项。
- **输出**：端到端测试矩阵、实机截图/记录、性能与失败回退结论、已知限制、发布/回滚清单。
- **完成条件**：关键端到端流程通过；目标显示设备长期运行、Agnes 真实包装集、PWA/扫码和食谱真实文本均有通过证据或已启用的降级方案；无阻塞级安全问题。
- **人工验收**：按测试矩阵在真实手机、目标显示设备和至少一个非 PWA 浏览器完成“配对 → 创建布局 → 手工录入 → 查看 → 食谱扣减/撤销 → 撤销设备”全链路，并保留截图、版本和失败回退记录。
- **依赖**：P3、P6、P8、P9、P10。

### P12：远程性能紧急修复（Backlog 最高优先级）

- **目标**：优先消除已知的远程卡顿放大器，让“我的冰箱”列表、打开冰箱、打开设置和应用启动不再因为重复请求、过量并发或 SQLite 写锁而明显停顿。
- **已确认问题**：
  - “我的冰箱”对每台冰箱预加载 `layout + inventory`；5 台冰箱至少产生 10 个请求，日志中还出现完整重复的一轮。
  - 打开一台冰箱要同时等待 6 个接口，打开设置还要追加设备接口，且没有立即反馈和防重复点击。
  - 启动请求没有超时，“正在准备”可能无限等待；提醒接口会立即调用并每分钟轮询。
- **范围**：只处理上述已知问题及其直接回归测试；不在本任务中开展完整监控平台、全面查询重构、缓存策略重做或部署架构升级。
- **实施顺序**：
  1. **P12.1 前端请求削减**：移除冰箱切换页对所有冰箱的完整 `layout/inventory` 预加载；列表只显示已有资料或轻量摘要，点击后再加载目标冰箱。打开冰箱和打开设置按页面实际需要懒加载分类、图标、临期规则、通知设置和设备列表。
  2. **P12.2 请求并发保护**：为当前冰箱加载增加 in-flight 去重或取消旧请求；点击冰箱/设置后立即显示加载和禁用状态；避免同一操作触发同一 URL 的多次请求，并保证旧请求不能覆盖新选择。
  3. **P12.3 启动和提醒兜底**：给统一请求增加超时和可重试错误状态，确保“正在准备”不会无限持续；提醒轮询至少只在页面可见时运行，并避免当前页面因重复挂载产生重复立即调用。
  4. **P12.4 紧急远程验收**：发布前后只比较本任务相关的请求数量、重复请求、页面可见反馈、SQLite 锁错误和冷启动失败；确认 Docker 生产构建和旧 Service Worker 场景，不扩展为完整性能平台建设。
- **约束**：保持同域 API/PWA、单 FastAPI/Uvicorn 进程、单容器副本和 SQLite WAL；不改变冰箱、库存、权限和提醒每日去重语义；不缓存 API 或返回过期业务数据；保留无网络时的现有应用壳行为。
- **完成条件**：
  - 5 台冰箱进入“我的冰箱”时，不再产生 5 台冰箱各自的完整 `layout/inventory` 请求瀑布；同一用户操作不会重复请求同一资源。
  - 点击冰箱或设置后立即出现可见的加载/禁用反馈；目标页面不再必须等待与当前页面无关的接口；请求失败或超过约定时限后显示可重试错误。
  - 应用冷启动不会无限停留在“正在准备”；提醒轮询不会因重复挂载产生额外的立即请求。
  - 远程 Network waterfall 和后端日志能证明重复请求数量、页面等待接口数量及 SQLite 锁错误均已下降或归零。
- **自动化验证**：补前端请求去重、加载状态、超时和提醒轮询测试；运行 `uv run ruff check backend`、`uv run pytest`、`npm run --prefix frontend lint`、`npm run --prefix frontend test`、`npm run --prefix frontend build`、`uv lock --check` 和 `docker build --tag fridgeboard:local .`。
- **人工验收**：准备至少 5 台冰箱，在远程移动网络或 DevTools 限速下执行“打开应用 → 我的冰箱 → 打开另一台冰箱 → 设置 → 返回 → 再切换”；确认每次点击立即反馈、无重复请求瀑布、无无限加载、数据不串；再打开两个标签页和一个已安装 PWA，确认提醒不会额外放大请求。
- **依赖**：P7、P7.1、P10 当前实现；P12.1–P12.3 完成后才能执行 P12.4 远程发布验收。

### P13：Capacitor APK/IPA 与 PWA 共存部署

- **当前阶段**：P13.1–P13.5 已实施，P13.3–P13.5 待真实设备验收；P13.6 GitHub Release 构建流程进行中；P13.7 未开始。
- **目标**：在不维护第二套业务 UI 的前提下，为现有 React/Vite 手机端增加 Capacitor Android/iOS 原生壳；原生包内置静态应用资源，远程访问现有 FastAPI API，同时保留 PWA 的同域 Cookie、Service Worker 和免安装入口。
- **输入**：[手机端 APK/IPA 与 PWA 部署设计](../mobile-deployment-design.md)、[ADR-0004](../architecture/adr/0004-capacitor-mobile-and-pwa.md)、现有 `frontend/src/appApi.ts`、`frontend/src/main.tsx`、`frontend/src/edgeSwipeBack.ts`、P3 认证/配对实现、P10 Push 实现和单容器部署规则。
- **核心约束**：不采用 Electron；不重写 React Native；不把跨源 HttpOnly Cookie 当作 App 唯一认证方案；不得把长期 Token 放入 localStorage、URL、日志或剪贴板；PWA 行为必须保持兼容；业务数据第一阶段不承诺离线读写；生产仍为单 FastAPI/Uvicorn 进程和 SQLite。
- **实施顺序**：必须按 P13.1 → P13.2 → P13.3 → P13.4 → P13.5 → P13.6 → P13.7 顺序推进。P13.1 或 P13.3 的 Spike 若证明技术边界不可行，暂停后续任务并重新评估，不在业务代码中堆平台特判。

#### P13.1：Capacitor 骨架和工具链 Spike

- **目标**：建立最小 Capacitor 工程，将现有 `frontend/dist` 打入 Android/iOS，验证本地静态资源启动、远程 API 连通、基础返回和权限能力。
- **输出**：实际目录结构、Capacitor/Android/iOS/Xcode/Gradle 版本、最低系统版本、开发和 Release 构建命令、首个 APK/IPA/AAB 体积基线、真机/模拟器记录；不实现正式认证。
- **自动化验证**：前端 lint/test/build；Android debug/release 构建；iOS archive（macOS/Xcode 环境）；`git diff --check`。
- **人工验收**：Android 和 iOS 各至少一台设备/模拟器，在飞行模式确认 App 壳可启动并显示内置页面；联网后确认一个只读 API 请求；按返回键/边缘返回一次；拒绝相机权限后页面仍可手工操作。
- **依赖**：ADR-0004 和移动端部署设计已评审；不依赖 P12 完成，但如 P12 修改 `appApi.ts`，需先读取最新实现。

#### P13.2：运行时、API 基地址和 PWA 回归

- **目标**：增加 `web/capacitor` 运行时适配，统一 API base URL、SSE、上传、超时、取消和错误处理；PWA 继续使用相对同源 API 和 Service Worker。
- **输出**：运行时配置/原生桥接边界、API 适配测试、无 Service Worker 原生启动策略、开发/生产配置说明。
- **实现备注**：Capacitor 默认本地 Origin（Android `https://localhost`、iOS `capacitor://localhost`）由 FastAPI 仅按明确白名单提供 CORS；登录跳转、图标和候选 PNG 统一解析到远程 API Origin。Android 构建通过标准 `JAVA_HOME`/Android Studio Gradle JDK 选择 Java 21，不提交本机绝对路径。
- **自动化验证**：覆盖 PWA 相对路径、Capacitor 绝对 HTTPS API、SSE、图片上传、401/超时/取消；运行后端与前端最低质量门禁。
- **人工验收**：PWA 清缓存打开、原生 App 飞行模式打开静态壳、联网后执行库存读取和一条 SSE/上传流程；确认没有跨源 Cookie 误判和重复请求。
- **依赖**：P13.1、P12 当前相关改动稳定。

#### P13.3：App 会话、安全存储和撤销

- **目标**：实现系统浏览器 SSO 后的 App 会话交换/刷新/退出，并为日常设备凭证提供 Bearer 请求；凭证存入 Android Keystore/iOS Keychain。
- **输出**：必要的后端会话协议/迁移、原生安全存储桥、前端认证适配、撤销和 401 清理逻辑、日志脱敏规则。
- **安全要求**：使用一次性 code + state/PKCE；长期凭证不进 URL、localStorage、日志、剪贴板或普通 WebView Cookie；服务端可按 App 会话/设备撤销；App 自报标识不能提升权限。
- **自动化验证**：有效/过期/重复 code、state 不匹配、刷新轮换、退出、撤销后 401、凭证不落盘到 Web Storage、日志不含敏感值；后端异常链和关键认证上下文符合日志约定。
- **人工验收**：Android/iOS 真机完成登录、杀进程重启、退出、服务端撤销和重新登录；用配对设备完成日常访问，确认 owner/daily 权限不串。
- **本次实现证据**：新增迁移 `20260814_23`、`/api/auth/mobile/exchange|refresh|logout`、PKCE/state 回跳、Owner/设备 Bearer 分流、按冰箱选择设备凭证、Capacitor 401 处理和 Android Keystore/iOS Keychain 原生桥；后端 156 项测试、前端 176 项测试、Android Debug 和 iOS Simulator Debug 构建已通过。真实设备人工验收未完成。
- **依赖**：P13.2；必须先完成认证方案评审再新增迁移或公开 API。

#### P13.4：App Links、Universal Links 和二维码配对

- **目标**：让公开登录/配对 URL 在已安装 App 时进入 App，未安装时进入 PWA；完成系统浏览器 SSO 回调和短效配对 token 消费。
- **输出**：`assetlinks.json`、`apple-app-site-association`、域名/包名/签名关联配置、服务端回调、App 深链处理、PWA fallback。
- **自动化验证**：路径白名单、state/token 清理、过期/重复消费、错误域名/恶意参数、未安装回退；后端和前端相关测试。
- **人工验收**：分别测试 App 已安装、未安装、冷启动、后台恢复、二维码来自 Kindle/浏览器、扫码取消、Token 过期和重复扫码；确认 URL 中不残留长期凭证。
- **依赖**：P13.3；必须有正式包名、Team ID、签名指纹和公开 HTTPS 域名。

#### P13.5：相机、扫码、分享、通知和系统手势

- **目标**：接入必要原生能力，并保持 PWA fallback；Android 接入系统 back/predictive back，iOS 接入 WKWebView 返回手势，避免与现有页面级手势冲突。
- **输出**：集中式 native bridge、相机/扫码/分享/网络状态/安全区适配、Android/iOS 手势配置和回归测试。
- **自动化验证**：原生桥不可用时 Web fallback；权限拒绝/取消；重复返回不触发两次；抽屉、表单、横向列表和扫码页手势边界。
- **人工验收**：Android 12–15+ 至少覆盖返回手势、键盘、模态框和扫码；iOS 至少覆盖首页、二级页、抽屉、未保存表单和扫码页；相机拒绝后可手工录入；推送若未满足平台条件必须显示明确降级状态。
- **依赖**：P13.4；P6/P10 既有浏览器能力不能被原生路径破坏。

#### P13.6：构建、签名、发布和商店准备

- **目标**：形成不依赖应用商店的签名 Android APK 与 iOS IPA 构建、校验和当前公开仓库 GitHub Release 发布流程；保留未来 AAB/TestFlight 的扩展边界。
- **输出**：`scripts/mobile-release.sh`、`.github/workflows/android-release.yml`、`.github/workflows/mobile-release.yml`、原生版本/签名注入、APK/IPA 包内元数据校验、Actions artifact、GitHub Release 资产、既有 iOS/flycn 兼容入口、产物和回滚说明。
- **约束**：密钥不进 Git 或日志；debug 包、模拟器 `.app` 和未签名 archive 不得上传；同一仓库使用 Actions 内置 `GITHUB_TOKEN`；不修改 Google Play、Apple App Store 或 TestFlight 状态。
- **自动化验证**：脚本语法、dry-run、前端门禁、Android release APK/AAB、iOS device archive/IPA、包名/版本/构建号校验和敏感文件扫描。
- **人工验收**：安装测试版、升级、卸载重装、签名验证、App Links/Universal Links、PWA 发布后 API 兼容；记录 APK/AAB、IPA、商店下载和安装占用的实际数据。
- **依赖**：P13.5、项目 Apple/Google 开发者配置和正式签名环境。

#### P13.7：双轨端到端验收

- **目标**：证明 PWA、Android App、iOS App 三条入口共享业务语义且互不回归。
- **自动化验证**：全量后端/前端门禁、移动端构建门禁和必要的真机自动化/契约测试。
- **人工验收**：按设计文档矩阵完成登录、配对、创建/切换冰箱、手工录入、扫码、图片上传、SSE、食谱/购物、返回手势、断网静态启动、凭证撤销和版本升级；记录设备、系统、WebView/WebKit、App/API release、截图和失败回退。
- **完成条件**：PWA 同源 Cookie/Service Worker 无回归；App 包内静态壳在清缓存/飞行模式可打开；App 认证和深链通过；凭证可撤销且无敏感泄漏；Android/iOS 系统手势通过；商店/签名产物可复现；无阻塞级安全或数据一致性问题。
- **依赖**：P13.1–P13.6 全部完成；P11 端到端发布准备可复用其测试矩阵。

## 4. 会话结束的交接格式

每个任务包结束时，将以下内容填入进度看板的会话记录：

```text
任务：P?
状态：完成 / 阻塞 / 进行中
改动：<文件与关键行为>
验证：<命令> — 通过/失败及原因
未验证：<原因与风险>
待决策：<需要产品或架构确认的问题；没有则写“无”>
下一步：<下一个可领取任务及其输入>
```

不要仅以“代码已写完”作为完成标准；必须满足任务包的完成条件并留下验证证据。
